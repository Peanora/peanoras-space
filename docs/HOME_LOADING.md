# 首页首次加载优化

日期：2026-11-10。对应反馈：“感觉进首页首次加载字体和图片很慢，可以优化吗？”本轮在本地完成，未推送或部署。

## 原因与改动

- 原 Core 字库没有覆盖近期导航、侧栏、曲名与笔记标题中的文字。首页因此额外加载十四个文楷分包。`prepare-wenkai.py` 现在按首页和公共界面生成 Core（573 字符、115,256 字节），笔记正文仍按 Unicode 分包加载。保留文楷、Nunito、Kalam 的原始字形、许可与 `font-display: swap`。完整字库继续只作生成源。
- 三个主题的场景在首次翻到时挂载，之后保持挂载，避免隐藏场景抢先下载大图，也保留返回时的纸条状态。`ArtworkImage` 默认原生懒加载；可见封面与详情横幅明确立即加载。
- 两张很小的音乐/纸条书签改用已有 240px 副本；其余前景插画增加 240px 响应式候选。整页浅背景只用 640px 副本，前景插画仍根据尺寸和像素密度选择清晰版本。未修改原始图片。
- 比较过 HTML 预加载全部字体：虽提前完成字体请求，但在限速测试中会挤占 CSS/JS 带宽、延后首屏出现，最终未采用。

数据流：内容 JSON 与公共组件 → 可选字体生成脚本 → Core 和互不重叠的分包/CSS → 浏览器按可见文字请求。翻屏 → 首次挂载场景 → 按尺寸请求 WebP → 再次翻回保留组件状态。

## 冷缓存对比

本地生产构建，Playwright Chromium，禁用缓存并清空浏览器缓存；下载速率 200,000 B/s（约 1.6 Mbps）、延迟参数 100ms，不限制 CPU。桌面 1440×900、DPR 1；手机模拟 390×844、DPR 3。每组是单次观测，不代表线上测速或真实手机结果。字体/图片大小为 Resource Timing 的 `encodedBodySize`，字体完成时间为最后一个字体响应结束，均从导航开始计时。

## 验证与边界

- `npm test`：55/55 通过，包括生产构建、编辑器隔离、本机音频排除与字体分包完整性。新增检查确认所有字体范围互不重叠，总计仍覆盖上游 25,694 字符，CSS 不引用完整字体。
- `npm run build`：通过。
- 生产预览：桌面逐屏翻到 World、Music、Little Things，当前屏图片均完成加载；纸条可打开；笔记正文可直接访问。手机宽度验证导航、个人侧栏、Escape 关闭、键盘翻屏，无横向溢出或可见坏图；打开/收起侧栏时仍只有一个 audio，初访无 iframe。浏览器控制台无错误或警告。
- 仍需用户在真实手机、实际网络下体验；未测试 Safari、Firefox 或屏幕阅读器。本机结果不能保证 GitHub Pages 在所有网络中的响应时间。
- 首次翻到主题才下载其大图，慢网下可能短暂等待；再次翻回保留已加载场景。新增文字仍有分包兜底，常规内容修改与构建不要求运行 Python。新增较多首页文字后可再生成 Core。
